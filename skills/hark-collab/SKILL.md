# 与 Hark 协作开发

`ask_hark` 有六个参数，**没有 `message` 参数**：

| 参数 | 必填 | 放什么 |
| :-- | :-- | :-- |
| `mode` | 是 | `plan` 要方案 / `review` 要审查 / `chat` 普通提问 |
| `user_request` | 是 | 用户原话，原样粘贴，不要改写 |
| `analysis` | 是 | 你自己写的分析：目标、验收标准、涉及的模块/文件、技术栈与约束、你倾向的做法。空着会被工具拒绝 |
| `context` | 否 | 目录结构、相关文件的关键代码；`review` 时放 `git diff` 与测试输出 |
| `questions` | 否 | 你不确定、需要 Hark 拍板的点 |
| `attachments` | 否 | 要一起发过去的工作区相对路径数组，如 `["docs/plan.md","src/a.ts"]` |

Hark 看不到本机文件，**代码必须进 `context` 或 `attachments`**。单条正文上限见配置 `maxChars`（默认 60000 字符），超了会被拒绝。

**长内容优先用 `attachments`，不要塞进 `context`**：附件是真正的文件上传，格式、行号、diff 都保真，还省你的上下文。`context` 只放 Hark 必须当场看到的关键片段。

`analysis` + `context` 拼起来超过 `attachBodyMinChars`（默认 4000 字符）时，插件会自己把它们写成一个 `正文-<编号>.md` 传过去，聊天里只剩一句「请以附件为准」——**这是保真措施**，不必为了避开发附件而硬压内容。返回值里会有一条 `正文 N 字符超过…，已改写成附件 …` 的提示，看到它就知道 Hark 收到的是文件而不是聊天正文。

## 返回值是文件，不是全文

工具返回值形如：

```text
请求编号 l46i4dbvk　模式 plan
📄 完整回复已保存：.hark/replies/2026-10-22-2143-plan-l46i4dbvk.md
（需要全文请直接读这个文件；下面只是开头部分。）

## 方案
…（已截断）
```

**看到「已保存」，就先用 read 工具把那个文件读完，再动手实现或按审查意见改。** 返回值里的预览只有开头 1200 字，照它干活会漏掉后半截的要求。

Hark 如果额外附了 `.md` 文件，会多一行 `📎 Hark 附带的文件已下载（<文件名>）：…`——那份是原文，比气泡里的渲染文本完整得多（气泡会吃掉 Markdown 符号、压掉空行），**以文件为准**。有的情况下文件就是回复本身，这时返回值里只出现一行路径，不会再有单独的「已保存」。

**回复里没文件、只有正文**：说明这次 Hark 没生成 `.md`（一两句话就答完的问题，或它在正文里写了「无法生成文件」）。这时正文就是全文，不用去找文件。plan/review 都拿到正文却没文件时，值得在下次请求里提醒它一次。

规则要求 Hark **plan/review 一律写 `.md` 附件**，`chat` 在回复超过 300 字左右时也写。所以：
- `plan` / `review` 拿到的是正文而没有文件 → 它没照做，下次请求时提一句；
- `chat` 拿到长正文却没文件 → 也可能只是差几十字没到门槛，不必追问。

## 流程

1. **要方案**：`ask_hark(mode="plan")`，先自己读项目再填 `analysis` 和 `context`。长方案、成段代码放 `attachments`。
2. **读文件**：拿到返回值里的 `.hark/replies/…md` 路径，**先 read 全文**，再开始干活。
3. **执行**：按方案里的任务清单拆分，能并行的派给子代理；每个子代理只拿它那一块的上下文和验收标准。
4. **审查**：全部完成后运行测试，再 `ask_hark(mode="review")`，`context` 放 `git diff`（太大就按模块分几次，或用 `attachments` 传 patch 文件）和测试结果。同样先读落盘文件再照着改。
5. **修改**：按审查意见里“必须修改”的条目改完，再 review 一次，直到结论为“通过”。
6. 向用户汇报：方案摘要、改动文件、审查结论。落盘的文件路径也告诉用户，他们想自己翻更方便。

## 协议（插件自动处理，了解即可）

每个 Hark 地址第一次被调用时，插件先单独发一条规则说明过去（消息格式、回复末尾必须写 `[[DSH-END#<同一个编号>]]`、编号要一致），Hark 回「规则已收到」就算握手完成，之后不再重复发。所以第一次调用会多花一次往返，属正常现象；换了新的 Hark 页面地址会重新握手一次。

## 出错时

- `Hark 在 N 分钟内没有给出结束标记` —— 超时，回复被截断。错误里会附上已收到的部分，但那**不是完整结论**，不要拿去当方案或审查通过的依据。可以调大 `timeoutMin` 或把需求拆小后重试。
- `找不到 Hark 输入框` —— 需要先登录，或者 `harkUrl` 指的不是对话页面：让用户执行 `/hark-login` 把页面切到前台登录一次，再确认 `/hark-url` 当前值。
- `ego 还没完成初始化引导` —— 用户的 ego 浏览器没在运行或首次启动没走完引导。让用户先打开 ego 正常用一次，再重试。
- `请先设置 harkUrl` —— 地址没设或设错了。让用户执行 `/hark-url`（不带参数看当前值），或 `/hark-url <网址>` 改掉。
- `附件已跳过：…` —— 某个文件没发过去（越界、敏感文件、超大）。不是致命错，但要告诉用户少了什么。整批都不可用会直接报错。
- `（附件未能上传，已改为把文件内容贴在消息正文里）` —— 附件上传超时，已降级成内联。内容没丢，但格式可能被压平；如果 Hark 需要精确保真，重试一次。
- `回复文件没能保存：…` —— 落盘失败（目录不可写、`replyDir` 越界）。回复仍然拿到，只是没文件，返回值里是全文。
